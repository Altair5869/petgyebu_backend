## 판단이 필요했던 지점

### 1. "우리 주석을 걷어낸 나머지"를 어떻게 정의할 것인가

원본의 첫 줄이 `-- Autogenerated: do not edit this file`라 **주석이다.** "맨 앞의 `--` 줄을
전부 버린다"는 규칙을 쓰면 원본의 첫 줄까지 같이 버려져, 그 줄이 사라져도 테스트가 통과한다.

그래서 명시적 마커 한 줄을 쓴다.

```
-- >>> BEGIN spring-batch-core schema-postgresql.sql >>>
```

이 줄 **다음 바이트부터 파일 끝까지**가 비교 대상이다. 원본의 첫 줄도 마지막 개행도 비교에
포함된다. 테스트는 마커를 찾지 못하면 그 자체로 실패한다.

비교는 `ISO-8859-1`로 디코딩한 문자열끼리 한다. 이 인코딩은 바이트와 문자가 1:1이라
바이트 비교와 동치이면서, 실패했을 때 assertj가 읽을 수 있는 diff를 보여준다.

### 2. `BatchConfig`를 추가한 것 — 범위를 넘은 판단

Task 범위는 "마이그레이션"이지만 **완료 기준 3(Job이 실제로 실행되어 메타 테이블에 기록이
남는다)을 마이그레이션만으로는 달성할 수 없었다.**

Spring Batch 6.0의 `DefaultBatchConfiguration#jobRepository()`는
`ResourcelessJobRepository`를 돌려준다(5.x와 달라진 점). Boot 4의 `BatchAutoConfiguration`이
이 클래스를 상속하므로, DataSource가 있어도 메타데이터가 **메모리에만** 남는다. Job은 예외 없이
`COMPLETED`로 끝난다. 진단 과정은 `docs/11-troubleshooting-log.md` 22번에 남겼다.

최소 크기로 고쳤다 — 빈 `@Configuration` 클래스에 `@EnableBatchProcessing` +
`@EnableJdbcJobRepository`(6.0 신규 애노테이션) 둘뿐이고, 속성은 전부 기본값이다.

### 3. Job을 `@Bean`으로 두지 않았다

빈으로 선언하면 Boot의 `JobLauncherApplicationRunner`가 컨텍스트 기동 중에 실행할 수 있어,
테스트가 무엇을 돌렸는지 불분명해진다. 테스트 메서드 안에서 `JobBuilder`/`StepBuilder`로
직접 만든다. 운영 코드에는 Job이 하나도 추가되지 않았다.

### 양방향: 변이를 넣고 각 테스트가 어떻게 반응하는가

세 변이 모두 적용 → 실행 → 원복했고, 원복 후 sha256이 원본과 같은 것을 확인했다.

**변이 A — `JOB_NAME` → `JOB_TITLE` (컬럼 정의 1곳)**

```
2 tests completed, 2 failed
  FAILED BatchSchemaSourceTest  : org.opentest4j.AssertionFailedError (마커 아래 구간이 원본과 다르다)
  FAILED BatchJobExecutionTest  : java.lang.IllegalStateException (Failed to load ApplicationContext)
      Caused by: org.flywaydb.core.internal.exception.FlywayMigrateException:
                 Failed to execute script V202609221408__create_spring_batch_metadata.sql
      Caused by: org.postgresql.util.PSQLException: ERROR: column "job_name" named in key does not exist
```

**둘 다 걸린다.** 다만 이 변이는 `JOB_INST_UN` 유니크가 `JOB_NAME`을 참조해서 **DDL 단계에서**
터진다. 즉 원본 일치 테스트가 없어도 Flyway가 잡아 줬을 변이다. 그래서 더 어려운 쪽을 따로 돌렸다.

**변이 A′ — `EXIT_MESSAGE` → `EXIT_MSG` (`BATCH_JOB_EXECUTION`, 제약이 참조하지 않는 열)**

```
4 tests completed, 2 failed
  FAILED BatchSchemaSourceTest  : 마커 아래 구간이 원본과 다르다
  FAILED BatchJobExecutionTest  : org.springframework.jdbc.BadSqlGrammarException:
      bad SQL grammar [INSERT INTO BATCH_JOB_EXECUTION(JOB_EXECUTION_ID, JOB_INSTANCE_ID, START_TIME,
      END_TIME, STATUS, EXIT_CODE, EXIT_MESSAGE, VERSION, CREATE_TIME, LAST_UPDATED) VALUES (?,...)]
      Caused by: org.postgresql.util.PSQLException:
                 ERROR: column "exit_message" of relation "batch_job_execution" does not exist
  (PostgresMigrationTest 2건은 통과)
```

**이것이 핵심 결과다.** `CREATE TABLE`은 전부 성공하고 `PostgresMigrationTest`도 초록불인데,
`JdbcJobRepository`가 INSERT를 날리는 순간 터진다. 기존 마이그레이션 테스트만 있었다면
이 변이는 그대로 통과했을 것이다.

**변이 B — `CREATE SEQUENCE BATCH_JOB_INSTANCE_SEQ` 한 줄 삭제**

```
4 tests completed, 2 failed
  FAILED BatchSchemaSourceTest  : 마커 아래 구간이 원본과 다르다
  FAILED BatchJobExecutionTest  : org.springframework.dao.DataAccessResourceFailureException:
                                  Could not obtain sequence value
      Caused by: org.postgresql.util.PSQLException:
                 ERROR: relation "batch_job_instance_seq" does not exist
  (PostgresMigrationTest 2건은 통과)
```

테이블 6개는 전부 만들어진다. `ddl-auto: validate`도 통과한다. 배치가 ID를 뽑는 시점에만 드러난다.

### 두 테스트의 역할이 갈린다

| 변이 | 원본 일치 | Job 실행 | PostgresMigrationTest |
|---|---|---|---|
| A `JOB_NAME`→`JOB_TITLE` | 걸림 | 걸림(Flyway 단계) | 걸림 |
| A′ `EXIT_MESSAGE`→`EXIT_MSG` | 걸림 | 걸림(INSERT 단계) | **통과** |
| B 시퀀스 1개 삭제 | 걸림 | 걸림(ID 채번) | **통과** |
| Spring Batch 버전 업(가정) | 걸림 | 통과할 수도 있음 | 통과 |

원본 일치 테스트는 **모든** 변이를 잡지만 "왜 문제인가"는 말해 주지 않는다. Job 실행 테스트는
**실제로 못 쓰게 되는 것만** 잡되 어디서 터지는지 보여준다. 둘 다 필요하다.
