## FIX-2 — `spring.batch.jdbc.initialize-schema`는 Boot 4.0에 없는 속성이다
- 판정: **FIX** (문서·주석 정확성. `application.yaml`은 지시대로 건드리지 않는다)
- 위치: `src/main/resources/db/migration/V202609221408__create_spring_batch_metadata.sql:14`,
  `src/main/java/com/petgyebu/telo/config/BatchConfig.java:23`
- 검증 대상: 두 주석이 주장하는 보호 장치 vs `spring-boot-batch-4.0.8.jar` 실물
- 사유: 두 주석 모두 "`spring.batch.jdbc.initialize-schema: never`라서 Flyway가 만든다"고 적었는데,
  **Boot 4.0.8에는 그 속성도 그 속성을 읽는 초기화기도 없다.**

```
$ javap -p …/boot/batch/autoconfigure/BatchProperties.class
  private final BatchProperties$Job job;          ← job 하나뿐. jdbc 없음
$ unzip -p spring-boot-batch-4.0.8.jar META-INF/spring-configuration-metadata.json | …
spring.batch.job.enabled
spring.batch.job.name                              ← 전부다
$ # spring-boot*-4.0.8.jar 전체에서 Batch…Initializer 클래스 검색 → 0건
```

  동작상 피해는 없다(Boot 4는 배치 스키마를 아예 자동 생성하지 않으므로 Flyway 소유가 유지된다).
  문제는 **근거가 틀렸다는 것**이다. 없는 속성을 방어선으로 적어 두면, 나중에 누군가
  "이 설정이 막아 주니 안전하다"고 믿거나 버전을 올릴 때 잘못된 기준으로 판단한다. 22번 항목이
  "5.x의 기억으로 기본값을 넘겨짚지 마라"를 교훈으로 적은 바로 그 유형이 주석 안에 남아 있다.
- 수정 지시: 두 위치의 문구를 "Boot 4.0에는 배치 스키마 자동 생성기가 없다. 이 스키마는 Flyway가
  만든다"로 바꾼다. `application.yaml:28`의 죽은 속성 제거와 `docs/05-infra-stack.md:137`의
  같은 서술 정정은 **T-040 범위 밖이므로 별도 Task로 등록**한다(이 커밋에서 고치지 말 것 —
