# T-025 입력 명세 — 예산 설정 API와 구간 검증 (+ 선행 T-003a)

작성: 2026-09-23. 대상 기능: **F-FZUVLV** (예산 기간 및 목표 설정).
브랜치: `feature/F-QJXRMD-token-access` (T-003a) → `feature/F-FZUVLV-api` (T-025).

## 0. 이 Task의 위상

**첫 로직 Task다.** 스키마 Task 일곱 개가 끝난 뒤 처음으로 컨트롤러·서비스·DTO·예외 처리가
생긴다. 여기서 정한 관례가 이후 모든 API Task의 기준이 된다. 스키마 Task에서 그랬듯 첫 Task의
선택이 나머지를 끌고 간다.

`src/main/java`에 `@RestController`도 `@Service`도 **아직 하나도 없다**. 참고할 기존 관례가
없으므로 이 문서가 관례를 정의한다.

## 1. 선행: T-003a (액세스 토큰 발급·검증)

### 왜 필요한가

`SecurityConfig`가 `anyRequest().authenticated()`이고 인증 수단이 없다. 지금 컨트롤러를 만들면
401만 나고 종단 검증이 불가능하다.

### 왜 T-003 전체가 아닌가

T-003의 리프레시 회전·폐기 토큰 재사용 감지는 폐기 상태 저장소로 Upstash Redis를 쓰기로 했고
(`docs/09-db-design.md` 2.2절), 아직 미프로비저닝이다(백로그 **B-REDIS**). T-025를 막는 것은
액세스 토큰 검증 경로뿐이므로 거기까지만 당긴다.

- **T-003a (이번 범위)**: 액세스 토큰 발급·검증 필터, `userId` 해석. Redis 불필요
- **T-003b (미루는 범위)**: 리프레시 발급·회전·재사용 감지·전 세션 무효화. Redis 프로비저닝 후

### 범위

| 항목 | 내용 |
|---|---|
| 발급 | `TokenService.issueAccessToken(User)`. **HTTP 엔드포인트는 만들지 않는다** — 카카오 인가 코드(T-002)가 없어 진입점이 없다. T-002가 붙을 때 그 컨트롤러가 이 서비스를 호출한다 |
| 만료 | 액세스 30분 (`docs/02-requirements-features.md` F-QJXRMD rules) |
| 서명 | HS256, `jjwt` 0.13.0(이미 의존성에 있음). 비밀키는 설정에서 주입, 운영은 환경변수 |
| 클레임 | `sub` = `users.id`. 그 이상 넣지 않는다 |
| 검증 | `OncePerRequestFilter`가 `Authorization: Bearer` 파싱 → `SecurityContext`에 인증 주체 설정 |
| 시각 | 발급·만료 판정에 `AppZone.clock()`을 쓴다. `Clock`을 주입받아 테스트에서 고정 시계로 바꿔 끼운다 |

### 검증 방법

테스트가 `TokenService`로 **진짜 토큰을 발급해** `Authorization` 헤더에 실어 보낸다. 모의 인증
(`@WithMockUser`)을 쓰지 않는다 — 필터·파싱·만료까지 실제로 지나가야 종단이 증명된다.

성공 기준:
- 유효 토큰 → 200, 컨트롤러가 받은 `userId`가 발급 시 `sub`와 같다
- 토큰 없음 → 401
- 서명이 틀린 토큰 → 401
- 만료된 토큰 → 401 (고정 시계를 만료 뒤로 옮겨 확인)
- `/actuator/health` → 토큰 없이 200 (기존 동작 유지)

## 2. T-025 범위

### 명세 출처

`docs/02-requirements-features.md` **F-FZUVLV**. 완료 기준은 `docs/10-task-backlog.md` T-025행:
> 0% 고정·오름차순·중복·공백·6단계 누락 검증이 각각 해당 행을 지목하며 저장을 막는다. 기본값 6단계가 프리필된다

### 스키마는 이미 있다 (T-023 완료, PR #16)

- `BudgetPeriod` — `user`, `periodStart`, `periodEnd`, `targetAmount`, `targetAmountSnapshot`(`updatable = false`), `status`, `createdAt`, `updatedAt`
- `StatusThreshold` — `budgetPeriod`, `statusCode`, `startRate`, `endRate`(OVER_BUDGET만 null), `sortOrder`, `updatedAt`
- **구간 검증과 경계값 판정은 DB가 아니라 애플리케이션이 맡는다**(`docs/09-db-design.md` 4.2절). `StatusThreshold` 주석이 그 로직을 T-025 범위로 지목하고 있다

### 기능 요구

1. **예산 기간 조회** — 현재 활성 기간의 목표 금액과 상태 구간 6행
2. **예산 설정 저장/수정** — 목표 금액 + 상태 구간 6행을 한 번에 받는다
3. **기본값 프리필** — 활성 기간이 없는 신규 사용자에게 기본 6단계를 채워 내려준다
4. **구간 검증** — 아래 다섯 가지. 각각 **어느 행이 문제인지 응답이 지목해야 한다**

### 구간 규칙 (F-FZUVLV rules)

- 첫 시작값은 **0% 고정**
- 각 구간은 이전 구간 끝값 다음부터 이어져 **공백 없음**
- 경계값은 **오름차순**, 동일 값 **중복 불가**
- `OVER_BUDGET`은 **100% 이상 고정** (끝값 없음)
- 6단계가 하나라도 누락되면 저장 불가
- 기본값: 휴식 0~40, 기상 40~60, 관심 60~75, 불안 75~90, 강한 경고 90~100, 예산 초과 100~

### 기간 규칙

- 매월 1일 00:00(KST) 시작, 말일 24:00(KST) 종료. **사용자가 시작일·길이를 바꿀 수 없다**
- 날짜 환산은 전부 `AppZone.KST`를 통한다. 존 없는 `LocalDate.now()` 금지
- 목표 금액 수정 시 `targetAmount`만 바뀌고 `targetAmountSnapshot`은 불변 (엔티티가 `updatable = false`로 이미 막아뒀다)

### 범위 밖 — 넣지 않는다

- **사용률 계산·경계값 판정은 T-026이다.** 오른쪽 닫힘 `(시작, 끝]` 판정 로직을 여기서 만들지 않는다
- **기간 자동 전환은 T-042(s9 배치)다.** 기간 종료·다음 기간 생성 로직 없음
- 소비 지출 집계는 T-024다. 이 API는 목표 금액과 구간만 다룬다
- 리프레시 토큰 관련 전부 (T-003b)

## 3. 정해야 할 관례 — 이 Task의 진짜 산출물

| 관례 | 결정 |
|---|---|
| 패키지 배치 | 기존 `budget/domain`·`budget/repository` 옆에 `budget/api`(컨트롤러·DTO)·`budget/service`. 도메인별 수직 분할을 유지한다 |
| 에러 응답 | **RFC 9457 `ProblemDetail`** (Spring 내장). 행 지목이 필요하므로 확장 필드에 위반 목록(어느 `statusCode` 행의 어느 규칙인지)을 싣는다 |
| 예외 처리 | `@RestControllerAdvice` 하나를 `common`에 둔다. 도메인 예외 → `ProblemDetail` 변환 |
| 검증 위치 | 단일 필드 제약(null, 범위)은 Bean Validation, **구간 간 관계 검증은 도메인 객체**가 맡는다. 컨트롤러에 검증 로직을 두지 않는다 |
| 인증 주체 | 컨트롤러가 `SecurityContext`에서 `userId`를 받는다. 경로에 `userId`를 넣지 않는다 |
| 시각 주입 | `Clock`을 빈으로 주입받는다. 서비스가 `OffsetDateTime.now()`를 직접 부르지 않는다 |

## 4. 로직 검증 축 (신설)

스키마 Task의 검증 축 7개는 정적 구조를 본다. 로직에는 맞지 않는다. 이 Task부터 아래를 쓴다.

| 축 | 묻는 것 | T-025 적용 |
|---|---|---|
| 1. 입력 검증 | 거부가 **어느 행을 지목하나** | 다섯 위반 각각 |
| 2. 경계값 | 규칙이 정한 양끝이 맞나 | 0% 고정, 100% 고정 |
| 3. 멱등성 | 두 번 저장해도 결과가 같나 | 같은 설정 재저장 |
| 4. 트랜잭션 경계 | 중간 실패 시 전부 롤백되나 | 구간 6행 중 하나 실패 |
| 5. 상태 전이 | 불가능한 전이가 거부되나 | 종료된 기간 수정 시도 |
| 6. 동시성 | 잠금이 실제로 걸리나 | T-025는 해당 약함. T-042에서 본격 |
| 7. 불변 필드 | 갱신 경로가 실제로 막히나 | `targetAmountSnapshot` |

**축 1·2는 양방향으로 증명한다** — 거부만이 아니라 **정상 입력이 통과하는 것도** 확인한다.
스키마 단계에서 "CHECK 허용만 넣고 거부를 안 봤다"로 구멍이 났던 것과 같은 실수를 뒤집어 반복하지
않기 위함이다.
