# T-040 입력: Spring Batch 메타 테이블 마이그레이션

- 브랜치: `chore/batch-schema`
- 의존: T-023(완료, PR #16)
- 막는 것: T-042(s9 예산 기간 전환 배치), T-043(크레딧 지급)

## 이 Task는 앞선 여섯과 성격이 다르다

지금까지는 `docs/09-db-design.md`에 **우리가 설계한** 스키마를 구현했다. **이번은 Spring Batch가 제공하는 스키마를 이식한다.**

| | T-006·T-013·T-014·T-023·T-031·T-041 | T-040 |
|---|---|---|
| 스키마 출처 | 우리 설계 문서 | **Spring Batch 6.0.5 제공 SQL** |
| 완료 기준 | 제약이 의도대로 동작하는가 | **원본과 일치하는가 + 배치가 실제로 도는가** |
| 검증 축 7가지 | 그대로 적용 | **대부분 적용되지 않는다** (아래 참고) |

백로그가 **"직접 작성하지 않는다"**를 굵게 적었다. 손으로 옮겨 적다 한 글자만 틀려도 런타임에 엉뚱하게 터진다.

## 원본 위치와 내용

**버전은 Spring Batch 6.0.5다.** 5.x가 아니다. 두 버전의 스키마가 다르므로 인터넷에서 찾은 예제를 붙여 넣지 마라.

```
/Users/taehun/.gradle/caches/modules-2/files-2.1/org.springframework.batch/spring-batch-core/6.0.5/12ce2792968d8ae708ba635861a45509b4f1176/spring-batch-core-6.0.5.jar
  → org/springframework/batch/core/schema-postgresql.sql
```

이 파일의 sha256은 `f2ac75cae966e4eb1cd97ee6b11f130495b7109153754a7983befb87614d6e38`이다.

**jar에서 직접 추출해 쓰라.** 내가 위에 내용을 붙여 두지 않은 것은 옮겨 적는 과정에서 오타가 생기는 것을 막기 위해서다. `unzip`으로 꺼내 그대로 복사하라.

빌드가 의존성 좌표를 어떻게 해석하는지 직접 확인하라. 버전이 다르면 위 경로도 달라진다. `./gradlew dependencies` 또는 `find ~/.gradle/caches -name "spring-batch-core-*.jar"`로 확인하고, 실제로 쓰이는 버전의 jar에서 꺼내라.

생성되는 것: 테이블 6개(`BATCH_JOB_INSTANCE`, `BATCH_JOB_EXECUTION`, `BATCH_JOB_EXECUTION_PARAMS`, `BATCH_STEP_EXECUTION`, `BATCH_STEP_EXECUTION_CONTEXT`, `BATCH_JOB_EXECUTION_CONTEXT`)와 시퀀스 3개.

## 고치지 마라 — 우리 관례와 어긋나는 것들

원본은 이 프로젝트의 관례를 **여러 군데 어긴다. 전부 그대로 둬라.** 고치면 Spring Batch가 돌지 않거나, 돌더라도 프레임워크 업그레이드 때 어긋난다.

| 원본 | 우리 관례 | 고치면 |
|---|---|---|
| `TIMESTAMP` | `TIMESTAMPTZ` (0장, T-052) | Spring Batch가 기대하는 타입과 달라진다 |
| `BATCH_JOB_INSTANCE` 대문자 | `snake_case` 소문자 복수형 | JdbcJobRepository가 테이블을 못 찾는다 |
| `CREATE SEQUENCE` | `GENERATED ALWAYS AS IDENTITY` | 프레임워크가 시퀀스에서 ID를 뽑는다 |
| CHECK 제약 없음 | 열거형에 CHECK | 원본에 없는 제약을 더하면 프레임워크가 쓰는 값이 막힐 수 있다 |
| `CHAR(1)` (`IDENTIFYING`) | `BOOLEAN` | 〃 |
| 파일 첫 줄 `-- Autogenerated: do not edit this file` | — | — |

**들여쓰기·공백·빈 줄·세미콜론 앞 공백까지 원본 그대로 두라.** 포맷을 다듬지 마라. 다음 버전과 대조할 때 diff가 커진다.

## 마이그레이션 파일

- 파일명은 `V{yyyyMMddHHmm}__{설명}.sql`, 버전은 `origin/main` 최대값보다 커야 한다
- **원본 SQL 위에 주석을 붙일 수 있다.** 어느 버전의 어느 파일에서 가져왔는지, sha256, "직접 수정 금지"를 적어라. 주석은 원본 SQL **바깥**에 두고 원본 줄은 건드리지 마라
- `spring.batch.jdbc.initialize-schema: never`가 `application.yaml:28`에 이미 설정돼 있다(Sprint 0). **바꾸지 마라.** Flyway가 관리한다는 뜻이다

## 검증 — 이번엔 축 7가지가 대부분 적용되지 않는다

`BATCH_JOB_INSTANCE`의 유니크에 "허용 케이스"를 단언하는 것은 뜻이 없다. 우리가 정한 규칙이 아니라 프레임워크가 정한 것이고, 우리는 그것을 바꿀 권한이 없다.

**대신 이 둘을 증명하라.**

### 1. 원본과 일치하는가

마이그레이션에서 우리 주석을 걷어낸 나머지가 jar 원본과 **바이트 단위로 같은지** 테스트로 단언하라.

- 테스트가 실행 시점에 클래스패스에서 `org/springframework/batch/core/schema-postgresql.sql`을 읽는다 (`ClassPathResource` 또는 `getResourceAsStream`)
- 우리 마이그레이션 파일도 읽는다
- 주석 부분을 제외하고 비교한다

**이 테스트가 이 Task의 핵심이다.** Spring Batch를 올릴 때 스키마가 바뀌면 이 테스트가 깨져 알려준다. sha256을 테스트에 하드코딩하지 마라 — 버전을 올리면 원본이 바뀌는 것이 정상이고, 그때 "원본과 우리 파일이 다르다"가 드러나야 한다.

### 2. 배치가 실제로 도는가

**테이블이 만들어졌다는 것만으로는 부족하다.** Testcontainers로 간단한 `Job` 하나를 정의해 실제로 실행하고, `BATCH_JOB_EXECUTION`에 `COMPLETED`가 남는지 확인하라.

이것이 "손으로 옮겨 적다 한 글자 틀린" 경우를 잡는 유일한 방법이다. 컬럼 이름이 하나 틀려도 `CREATE TABLE`은 성공하고, 배치를 돌릴 때가 되어서야 터진다.

`spring-boot-starter-batch-test`가 `build.gradle:69`에 이미 있다.

### 3. 그 외

- `PostgresMigrationTest` 통과 (Flyway 실행 + `ddl-auto: validate`)
- **기존 아홉 스키마 테스트 파일은 건드리지 마라**
- `./gradlew build --rerun-tasks` 통과

## 양방향 증명

- 마이그레이션에서 컬럼 이름 하나를 바꾸거나(`JOB_NAME` → `JOB_TITLE`) 줄 하나를 지우고 돌려, **일치 테스트와 배치 실행 테스트가 각각 어떻게 반응하는지** 보여라. 둘 중 하나만 걸리는지, 둘 다 걸리는지가 중요하다
- 시퀀스 하나를 지우고 돌려라 — `CREATE TABLE`은 전부 성공하지만 배치가 ID를 못 뽑는다
- 실제 출력을 인용하라

## 완료 기준
